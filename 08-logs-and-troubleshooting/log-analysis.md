# Linux Logs and Troubleshooting

Logs provide evidence about what an application or system was doing when a problem occurred. DevOps engineers use logs alongside metrics, traces, configuration, and recent changes to investigate incidents.

> **Goal:** Learn where logs may be found, how to read recent entries, filter messages, inspect the system journal, and follow a repeatable troubleshooting process.

## 1. What are logs?

A log is a record of events generated by an application, operating system, or service. Entries may include timestamps, severity levels, components, and messages.

Common severity labels include:
- `DEBUG` — detailed diagnostic information.
- `INFO` — normal operational events.
- `WARN` or `WARNING` — something unexpected that may need attention.
- `ERROR` — an operation failed.
- `CRITICAL` or `FATAL` — a severe failure, depending on the application's conventions.

Severity names and meanings vary by software. An `ERROR` entry is evidence to investigate, not automatically proof that the entire system is down.

## 2. Where Linux logs may live

On many Linux systems, text logs are stored under `/var/log`. Examples may include system, authentication, web server, or application logs, but filenames vary by distribution and configuration.

Inspect the directory if you have permission:

```bash
ls -lah /var/log
```

Some systems store much of their service logging in the systemd journal instead of traditional text files. Containers and cloud platforms may send logs to a central logging service. Always check the runbook and environment documentation.

Do not change or delete production logs as part of an investigation.

## 3. Read a text log safely

Use a log file that you are authorised to read. In this lesson, create your own sample log first:

```bash
mkdir -p ~/linux-for-devops-practice/day8
cd ~/linux-for-devops-practice/day8

cat > app.log <<'EOF'
2026-10-11 10:00:00 INFO application started
2026-10-11 10:00:02 INFO configuration loaded
2026-10-11 10:00:04 WARN request retry scheduled
2026-10-11 10:00:05 ERROR database connection failed
2026-10-11 10:00:06 INFO retrying database connection
2026-10-11 10:00:08 ERROR database connection failed
2026-10-11 10:00:10 INFO health check passed
EOF
```

Display the sample:

```bash
cat app.log
```

For a longer file, use:

```bash
less app.log
```

Press `q` to quit `less`.

## 4. Inspect recent entries

Show the first lines:

```bash
head -n 5 app.log
```

Show the last lines:

```bash
tail -n 5 app.log
```

Follow new entries as they are appended:

```bash
tail -f app.log
```

Press `Ctrl+C` to stop following. `tail -f` is useful for observing a file that is actively being written.

For live troubleshooting, be aware that applications may rotate log files or send logs to a journal or central platform rather than the file you are following.

## 5. Filter errors and warnings with `grep`

Find errors:

```bash
grep 'ERROR' app.log
```

Show line numbers:

```bash
grep -n 'ERROR' app.log
```

Ignore case:

```bash
grep -i 'error' app.log
```

Find warnings or errors:

```bash
grep -E 'WARN|ERROR' app.log
```

Count matching lines:

```bash
grep -c 'ERROR' app.log
```

Show context around each match:

```bash
grep -C 2 'ERROR' app.log
```

`-C 2` shows two lines before and after each match where available. Context can help reveal what happened before and after a failure.

## 6. Read systemd journal logs with `journalctl`

On a system using systemd, show recent journal entries:

```bash
journalctl -n 50
```

Follow new journal entries:

```bash
journalctl -f
```

Show messages since a recent time:

```bash
journalctl --since "1 hour ago"
```

Filter by a service unit, replacing `SERVICE_NAME` with the real unit name:

```bash
journalctl -u SERVICE_NAME -n 50
```

Filter for errors by priority:

```bash
journalctl -p err -n 50
```

The journal may contain sensitive information, and access can be restricted. Use only approved commands and avoid sharing unredacted logs publicly.

## 7. Check service status and logs together

If you administer a systemd service, inspect its status:

```bash
systemctl status SERVICE_NAME
```

Replace `SERVICE_NAME` with the correct unit name, for example `ssh` or `sshd` depending on the distribution.

Then inspect the service's recent journal entries:

```bash
journalctl -u SERVICE_NAME -n 100
```

Status output can show whether a service is active, failed, or recently restarted. Logs may show the reason, but not every failure has an obvious single error message.

These commands are for inspection. Restarting a production service can interrupt users and should follow the relevant runbook and approval process.

## 8. Search across several log files

Search all `.log` files in the current directory:

```bash
grep -n 'ERROR' ./*.log
```

Search recursively under a known practice or application directory:

```bash
grep -Rni 'ERROR' ./logs
```

Recursive search can be slow and may traverse files containing secrets or unrelated data. Narrow the search to a relevant, authorised directory.

## 9. Compare timestamps and build a timeline

When investigating a failure, note:
- The first observed failure time.
- The affected service or component.
- Error messages immediately before and after the failure.
- Any deployment, configuration, traffic, or dependency changes near that time.
- Whether the problem is ongoing or intermittent.

Use timestamps carefully: logs from different systems may use different time zones, formats, or clock settings. A timeline is more reliable when clocks are synchronised and time zones are understood.

## 10. A practical DevOps troubleshooting workflow

Imagine a service reports database connection failures.

1. **Define the symptom:** Which endpoint or operation fails, and when did it start?
2. **Check service status:** Is the application running or restarting?
3. **Read relevant logs:** Search for the error and nearby context.
4. **Look for patterns:** Is the error repeated? Does it affect all instances or only one?
5. **Check dependencies:** Investigate database availability, DNS, network connectivity, credentials, and connection limits as appropriate.
6. **Review recent changes:** Check deployments, configuration, secrets rotation, and infrastructure changes.
7. **Act safely:** Follow the runbook and avoid disruptive changes without approval.
8. **Verify recovery:** Confirm that error rates and user-facing symptoms return to normal.

Do not assume the first error in a log is the root cause. It may be a consequence of an earlier problem elsewhere.

## 11. Hands-on exercises

Use only the sample log created in your practice directory.

1. Display the entire log.
2. Show the last three lines.
3. Find all `ERROR` entries with line numbers.
4. Show two lines of context around each error.
5. Count how many error lines appear.
6. Save matching errors to `errors-only.log`.
7. Compare the original log and the filtered file.
8. If your system uses systemd and you have permission, inspect recent journal entries.
9. Write a three-step investigation plan for a service that started failing after a deployment.

Useful commands:

```bash
grep -n 'ERROR' app.log
grep -C 2 'ERROR' app.log
grep -c 'ERROR' app.log
grep 'ERROR' app.log > errors-only.log
wc -l app.log errors-only.log
```

## 12. Knowledge check

1. What is the difference between a text log and the systemd journal?
2. How does `tail -f` help during troubleshooting?
3. What does `grep -C 2` do?
4. Why should you inspect log context instead of reading only one error line?
5. Why is it important to understand timestamps and time zones?
6. Why should logs be redacted before sharing them?

**Suggested answers**

1. Text logs are written to files; the systemd journal is a logging system that stores structured entries and can collect service and system messages.
2. It displays new lines as they are appended to a file.
3. It displays two lines before and after each matching line, where available.
4. Nearby entries can show preceding events, retries, and downstream effects that help identify the cause.
5. Different clocks and time zones can make events appear out of order or mislead the incident timeline.
6. Logs can contain credentials, tokens, personal information, internal hostnames, and other sensitive data.
