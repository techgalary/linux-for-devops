# Linux Process Management

Processes are running instances of programs. DevOps engineers inspect processes to understand application behaviour, diagnose high CPU or memory usage, and investigate services that are not responding.

> **Goal:** Learn to list processes, inspect resource usage, understand process IDs and signals, and check service status without disrupting a real system.

## 1. Start with safe commands

You can run these commands in any normal Linux terminal:

```bash
whoami
date
uptime
```

`uptime` shows how long the system has been running, the number of logged-in users, and load averages. Load average is not the same as CPU percentage; interpret it alongside CPU count and other metrics.

## 2. What is a process?

A **process** is a running instance of a program. Each process has a Process ID (PID). Processes may start other processes, and many services run in the background.

A process can have:
- A PID — the process identifier.
- A parent PID (PPID) — the process that started it.
- A user identity — the account under which it runs.
- A state — for example, running, sleeping, or stopped.
- Resource usage — such as CPU time and memory.

## 3. List processes with `ps`

Show processes associated with your current terminal:

```bash
ps
```

Show a detailed list of processes:

```bash
ps aux
```

Show a process tree:

```bash
ps -ef --forest
```

Options and output can vary between systems. `ps aux` is a common Linux form, while `ps -ef` is another widely used format.

Search the process list for a name:

```bash
ps aux | grep '[s]sh'
```

The bracket pattern is a common way to avoid matching the `grep` command itself. Replace `ssh` with a process name relevant to your system.

## 4. Monitor processes interactively

Run:

```bash
top
```

`top` displays changing process and system resource information. Press `q` to quit.

If installed, you can also use:

```bash
htop
```

`htop` offers an interactive view, but it may not be installed by default.

Look for:
- Processes consuming a large amount of CPU.
- Processes using significant memory.
- Unexpected process names or users.
- Whether the issue affects one process or the whole system.

High usage is not automatically a fault. Correlate it with workload, logs, service health, and system metrics before acting.

## 5. Inspect a particular process

Find a process and note its PID:

```bash
ps aux
```

Then inspect that PID, replacing `1234` with the real PID:

```bash
ps -p 1234 -o pid,ppid,user,stat,%cpu,%mem,etime,cmd
```

This displays selected fields including the parent PID, owner, state, CPU and memory percentages, elapsed time, and command.

To list the processes in a tree format:

```bash
pstree -p
```

`pstree` may not be installed on every system.

## 6. Understand signals

Signals ask a process to perform an action.

- `SIGTERM` (often signal 15) requests that a process terminate gracefully.
- `SIGKILL` (signal 9) forcibly stops a process and cannot be caught or handled by it.
- `SIGINT` (often signal 2) is commonly generated by pressing `Ctrl+C` in a terminal.

See a command's help or manual for details:

```bash
kill --help
man kill
```

### Important safety practice

Do not terminate random processes. Identify the process, owner, command, and purpose first. Prefer a service manager or the application's documented shutdown method when stopping a service.

In a controlled lab, you can create a harmless sleep process:

```bash
sleep 300 &
```

The shell prints a job and/or PID. Inspect it:

```bash
jobs
ps -p "$!" -o pid,stat,cmd
```

`$!` expands to the PID of the most recently started background job in the current shell.

Request a graceful stop of that lab process:

```bash
kill "$!"
```

If you run other commands that launch background jobs in between, `$!` may refer to a different process. Use the PID you recorded if needed. You generally should not need `SIGKILL` for this exercise.

## 7. Check memory usage

Use:

```bash
free -h
```

This shows memory and swap totals in a human-readable format. On Linux, the `available` memory figure is often more useful than treating all memory shown as “used” as unavailable; the kernel uses memory for caches that can be reclaimed.

You can inspect memory information with:

```bash
cat /proc/meminfo
```

`/proc` exposes kernel and process information through a virtual filesystem; its contents are not ordinary files stored on disk.

## 8. Check CPU and load

Run:

```bash
uptime
top
```

In `top`, observe CPU usage and the load average. A high load average can indicate runnable work or tasks waiting on resources, including I/O. It does not by itself prove that CPU is saturated.

If installed, `mpstat` can provide CPU statistics:

```bash
mpstat
```

The command may be supplied by a package such as `sysstat`, depending on the distribution. Do not install packages on managed systems without authorisation.

## 9. Services and `systemctl`

Many Linux distributions use `systemd` to manage services. On such systems, `systemctl` can show service status.

For example, inspect the SSH service status without changing it:

```bash
systemctl status ssh
```

On some distributions, the service may be named `sshd` instead:

```bash
systemctl status sshd
```

A missing unit name does not necessarily mean SSH is not installed; service naming varies.

List active service units:

```bash
systemctl list-units --type=service --state=running
```

Check whether a service is enabled to start at boot:

```bash
systemctl is-enabled ssh
```

These are inspection commands. Starting, stopping, restarting, or enabling services changes system state and may require administrator privileges. Do that only when authorised and when you understand the impact.

## 10. Read service logs with `journalctl`

On systems using the systemd journal, inspect recent messages:

```bash
journalctl -n 50
```

Follow new system journal entries:

```bash
journalctl -f
```

Press `Ctrl+C` to stop following.

Inspect a particular service, replacing `ssh` with the appropriate unit name:

```bash
journalctl -u ssh -n 50
```

To view logs since a recent time:

```bash
journalctl --since "1 hour ago"
```

Access to some logs may be restricted. Do not expose secrets or sensitive log output when sharing troubleshooting results.

## 11. DevOps troubleshooting workflow

If an application appears unresponsive, investigate in a controlled order:

1. **Confirm the symptom:** What is failing, and when did it begin?
2. **Check service status:** Is the service active or reporting an error?
3. **Inspect logs:** Look for relevant errors around the failure time.
4. **Inspect the process:** Is it running? Which user owns it? Is resource use unusual?
5. **Check system resources:** Review CPU, memory, load, disk, and network indicators as appropriate.
6. **Choose the least disruptive action:** Follow the runbook or service owner's procedure.
7. **Verify recovery:** Check service health and confirm the original symptom is resolved.

Avoid restarting a service as the first step. A restart can interrupt users, hide evidence, or fail to address the root cause.

## 12. Hands-on exercises

1. Run `ps aux` and identify a process you recognise.
2. Run `top` and exit with `q`.
3. Run `free -h` and identify the available memory value.
4. Run `uptime` and observe the load averages.
5. Start `sleep 300 &`, inspect it, and stop only that test process.
6. If your system uses systemd, inspect a service with `systemctl status`.
7. If permitted, read recent journal messages with `journalctl -n 20`.
8. Write down the difference between a process and a service.

## 13. Knowledge check

1. What does PID stand for?
2. How does `ps` differ from `top`?
3. What is the difference between `SIGTERM` and `SIGKILL`?
4. Why is the `available` memory value useful?
5. Why should you inspect logs before restarting a service?
6. What does `systemctl status` tell you?

**Suggested answers**

1. Process ID.
2. `ps` provides a snapshot; `top` provides an updating interactive view.
3. `SIGTERM` requests graceful termination; `SIGKILL` forcibly stops a process.
4. It estimates memory available for new work, accounting for reclaimable memory.
5. Logs preserve evidence that may help identify the root cause; a restart may interrupt users or hide the original state.
6. It shows service status and related information, when the service manager and unit are available.
